## C2. 项目总体目标

本项目是面向大学「画法几何与工程制图」课程的互动教学平台，由三条并行的交付线组成：

1. **微信小程序（学生端，主体）**：点/线/面互动、基本立体、平面切割立体、尺规作图练习、AI 教师答疑。
2. **微信云开发后端**：`api` 云函数（学生端）与 `teacher` 云函数（教师端），彼此独立。
3. **网页教师后台**：`teacher-web/` 静态页面，经 CloudBase HTTP 网关调用 `teacher` 云函数。

它不是 CAD 系统。

所有改动优先服务于空间认知、投影理解与几何构造过程的可视化。

正确性、可解释性、交互反馈、可维护性高于功能数量。

禁止把制造、参数化建模或工程出图能力作为默认产品方向。

判断成功的标准是学生是否更容易看懂空间与投影的对应关系，而不是能画多少对象。

## C3. 技术栈

以下为经代码核对的实际技术栈，不得引入本节之外的运行时依赖。

| 层 | 技术 | 硬约束 |
| --- | --- | --- |
| 小程序端 | 原生 WXML / WXSS / JavaScript | 无构建步骤、无包管理器、运行时不依赖 Node.js |

| 教师网页 | 原生 HTML / CSS / JS | 无框架、无云 SDK，走 HTTP 网关 |
| 网页版几何演示 | 原生 HTML / CSS / JS | `web/index.html` 可直接用浏览器打开 |

禁止：React / Vue / Angular / Electron；必须经转译才能执行的语法；客户端构建链；新的第三方 CDN 运行时依赖。

允许开发者使用独立的静态分析与测试工具（例如 `node --check`），但客户端运行时不得依赖它们。

## C5. Agent 角色与职责边界

本项目采用三角色协作：**需求/架构 Agent**、**开发 Agent**、**测试/审查 Agent**。

同一时刻每个 Agent 只做本角色范围内的事；跨角色动作必须先交接，不得代做。

### C5.1 需求/架构 Agent

负责：把用户诉求转成可执行的任务定义；确认影响范围与冻结模块；给出技术方案、涉及文件与回归方案；判断哪些动作需要用户授权。

必须输出：任务定义（目标、非目标、验收标准）、影响文件清单、风险与回归清单、需要用户拍板的问题。

不得：直接大范围改写业务代码；在未获授权时批准冻结模块改动；发明不存在的技术栈、页面、集合、字段或接口。

### C5.2 开发 Agent

负责：按已确认的方案做最小侵入式实现；遵守第二部分技术规则；保持几何真值与渲染分离；完成自测与 `git diff` 检查。

必须输出：改动文件、关键设计决策、实际验证方式、已知限制、后续建议（模板见 §62）。

不得：顺手重构冻结模块；扩大方案范围；自行 `commit` / `push`；改动未获授权的冻结文件。

### C5.3 测试/审查 Agent

负责：独立复现与验证；核对需求、代码、文档三方一致性；检查冻结模块是否被动过、是否引入敏感信息；给出结论与证据。

必须输出：验证清单、实际执行方式（设备/尺寸/控制台）、未覆盖项、缺陷的复现步骤。

不得：边审边改业务代码（发现问题交回开发 Agent）；用“代码看起来合理”代替实测；声称存在本项目并不存在的自动化测试。

审查默认只读；确需修改时先说明并获得用户或任务负责人同意。

### C5.4 共同禁止

不得假设不存在的信息：技术栈、页面、集合、字段、接口、环境变量一律先查代码与文档后再断言。

不得覆盖或回滚他人（含用户）未提交的改动。

不得把密钥、密码、Token 写入代码、文档、注释或 Git。

## C6. 协作流程与交接

标准流转：

1. **需求/架构**：读代码 → 定范围 → 出方案与验收标准 → 需要授权处请示用户。
2. **开发**：按方案实现 → 自测 → 提交交付摘要。
3. **测试/审查**：独立验证 → 给出结论与证据 → 缺陷回传开发。
4. **需求/架构**：确认验收 → 用户确认后再提交。

交接必须携带上下文：任务定义、已确认的约束、改动文件清单、验证方式、未决问题。

交接不得只留“完成 / 未完成”结论。

同一时刻只允许一个 Agent 写同一文件；发现他人正在改的文件，先停下确认。

冲突升级：涉及冻结模块、数据库结构、教学资产（知识库与 Prompt）、部署链路、权限模型时，一律升级给用户决定。

## C9. 编码规范

除第二部分 §40–§47（命名、函数设计、类与组合、注释、CSS、HTML）外，本项目特有硬约束：

- 浮点比较不得使用严格相等，容差来自共享数值策略。
- 数值有限性必须在写入几何状态前校验，避免 NaN 传播。
- 与相邻文件风格保持一致；不做与本任务无关的格式化、重命名或重排。

## 2. 指令优先级

当前实现是**原生微信小程序 + 微信云开发**，另有一条**静态网页版**；本节的边界按这两条线理解，而不是浏览器单页应用。

场景根节点下应建立命名分组。

推荐分组为 `coordinateRoot`、`projectionPlaneRoot`、`geometryRoot`、`helperRoot`、`sectionRoot` 和 `interactionRoot`。

教学对象的可见模型与辅助线应放入不同分组。

拾取对象必须能追溯到领域对象 ID。

临时预览不得混入持久模型集合。

场景节点名称用于调试，不得作为唯一身份。

身份应通过稳定 ID 和显式映射管理。

## 8. 坐标系

默认采用右手笛卡尔坐标系。

X 轴为红色。

Y 轴为绿色。

Z 轴为蓝色。

原点记为 O。

世界单位默认视为抽象教学单位，不擅自标注毫米。

三维点统一表示为 `(x, y, z)`。

禁止在同一算法中混用轴语义。

若历史代码采用不同的竖直轴，必须在适配边界集中转换。

不得在多个模块散布轴交换代码。

坐标转换函数必须在名称中标明来源和目标。

例如 `worldToFrontView`、`worldToTopView` 和 `worldToLeftView`。

## 9. 投影面定义

H 表示水平投影面。

V 表示正立投影面。

W 表示侧立投影面。

H、V、W 的数学定义必须集中声明。

建议用单位法向量和有符号偏移表示平面。

平面方程统一为 `n · p = d`。

法向量写入模型前必须归一化。

平面姿态不得同时由欧拉角和法向量独立保存。

应选择一个权威表示，其余数据按需派生。

H 默认浅蓝色。

V 默认浅绿色。

W 默认浅黄色。

投影面材质必须支持透明度调整。

锁定状态只限制交互，不应改变数学定义。

## 10. 第一角投影

系统默认使用 ISO 第一角投影。

正视图、俯视图和左视图的展开关系必须在代码和教学文案中一致。

视图布局不能仅靠直觉放置。

投影符号约定应由一个配置对象集中定义。

每个三维点应通过同一投影管线生成三个二维点。

不得为点、线、平面和实体各自复制投影公式。

正视投影丢弃沿正视方向的深度分量。

俯视投影丢弃竖直分量，并按第一角展开约定定位。

左视投影丢弃侧向分量，并按第一角展开约定定位。

二维坐标必须与画布像素坐标分离。

模型视图坐标变换后，才应用缩放、平移和像素 Y 轴翻转。

缩放和平移不得改变几何投影结果。

## 11. 投影图元

投影结果应使用与三维对象相同的领域 ID。

正视、俯视和左视子图元应带有视图类型。

投影图元仅缓存派生数据。

领域对象变化时应标记相关投影为脏。

同一帧内多个变化应合并刷新。

可见轮廓使用实线。

不可见轮廓使用虚线。

中心线使用细点划线。

构造线使用低对比度细线。

投射对应线应可单独显示或隐藏。

线型规则必须集中定义，不得散落 CSS 和 JavaScript 魔法值。

## 12. 数学基础

纯几何函数不得修改输入参数。

返回对象的所有权必须清晰。

频繁路径允许使用调用方提供的输出向量以减少分配。

此类函数必须以 `out` 参数或注释明确说明。

向量比较不得使用严格浮点相等。

所有容差应来自共享数值策略。

推荐基础绝对容差 `EPSILON = 1e-8`。

屏幕合并与教学显示可使用更大的独立容差。

容差必须结合模型尺度。

推荐有效容差为 `max(EPSILON, scale * relativeEpsilon)`。

禁止用任意 `toFixed` 结果参与几何判断。

显示舍入只能发生在 UI 边界。

角度内部统一使用弧度。

界面可显示度数。

角度转换必须通过命名函数完成。

## 13. 点模型

点必须拥有稳定 ID、三维坐标、标签和可见状态。

标签默认按 A、B、C 顺序生成，但不得依赖标签作为 ID。

正视、俯视和侧视标签应由统一规则派生。

拖动点时必须即时更新坐标显示。

拖动约束应显式指定工作平面或轴。

禁止使用相机朝向变化导致不可预测的自由拖动。

坐标输入必须验证有限数值。

删除点前必须处理依赖它的线和平面。

依赖策略应是阻止、级联或失效标记中的一种，并在 UI 中说明。

## 14. 线模型

线由两个不同的点定义。

零长度线必须拒绝创建或标记为无效。

线的方向为归一化的端点差向量。

真长来自三维端点距离。

投影长度来自对应二维投影点距离。

倾角应相对于明确命名的投影面计算。

夹角计算前应钳制点积到 `[-1, 1]`。

线型分类必须基于方向与投影面法向量的关系。

分类判断必须使用容差。

同一条线只能有一个权威端点集合。

改变端点后所有度量必须重新派生。

## 15. 平面模型

三点定平面时必须检查三点不共线。

平面模型推荐保存单位法向量 `normal` 和常数 `d`。

若需要有限显示边界，应与无限数学平面分开表示。

显示平面的尺寸不应影响求交结果。

平面旋转必须围绕明确的枢轴和轴。

平面平移应更新 `d`，并保持法向量不变。

通过姿态控件改变法向量后必须重新归一化。

平面迹线是平面与 H、V、W 的交线。

平行或重合情形必须返回明确状态。

不得用超大线段假装所有迹线都有有限端点。

## 16. 实体领域模型

支持长方体、六棱柱、三棱锥、圆柱、圆锥和球。

实体模型必须保存类型、变换、参数和稳定 ID。

实体局部几何与世界变换必须分离。

移动只改变位置。

旋转只改变姿态。

缩放策略必须明确是均匀还是非均匀。

负缩放默认禁止。

实体参数必须有合理下限。

多面体实体应提供顶点、边和面的拓扑。

曲面实体应提供解析参数，而不是只暴露三角网格。

渲染细分等级不得决定数学求交精度。

## 17. 显示模式

实体支持实体、线框、透明和仅边线模式。

显示模式是渲染状态，不应改变领域几何。

不同实体应尽可能共享不可变材质模板。

对象级透明度不能通过克隆大量相同材质失控增长。

切换模式时必须清理不再使用的对象级资源。

边线颜色和宽度应满足课堂投影环境的对比度要求。

## 18. 截平面模型

截平面是独立领域对象。

它必须拥有法向量、偏移、显示尺寸、锁定和可见状态。

数学平面为无限平面。

显示网格只是操作手柄和视觉提示。

偏移沿单位法向量定义。

角度控件改变姿态，不得偷偷改变偏移。

平移控件的工作空间必须清晰。

截平面变化必须触发当前目标实体的截交更新。

连续拖动期间允许节流，但松手后必须精确刷新。

## 19. 多面体截交算法

多面体截交以拓扑边与无限截平面的交点为基础。

对每条边端点计算有符号距离 `s = n · p - d`。

若两端距离异号，则边与平面有唯一内部交点。

交点参数为 `t = s0 / (s0 - s1)`。

交点为 `p0 + t * (p1 - p0)`。

若端点距离在容差内为零，该端点属于截面。

若整条边共面，必须按共面边策略处理。

不得无条件把共面边的两个端点重复加入。

所有候选点必须按空间容差去重。

少于三个唯一点时不存在面状截面。

三个或更多点应投影到截平面的二维基底后排序。

排序不能直接使用世界 XY 平面。

应构造与法向量正交的稳定基向量 `u` 和 `v`。

基向量选择应避开与法向量近平行的参考轴。

以截点质心为排序中心。

按 `atan2(dot(q,v), dot(q,u))` 排序。

排序后应检查相邻重复点和零长度边。

凸多面体截面通常为单一凸多边形。

未来支持凹多面体时不得沿用单环假设。

## 20. 多面体退化情形

截平面完全位于实体外部时返回空结果。

截平面与单个顶点相切时返回点接触状态。

截平面沿一条边相切时返回线接触状态。

截平面与一个面共面时返回共面面状态。

这些状态不得伪装成普通截面多边形。

UI 应能以适当方式解释退化结果。

算法返回值应包含 `kind`、`points` 和诊断信息。

推荐 `kind` 值为 `none`、`point`、`segment`、`polygon` 和 `coplanarFace`。

## 21. 圆柱截交

圆柱截交优先使用局部坐标中的解析或半解析方法。

不得仅依赖当前渲染网格的三角形切片。

平面垂直圆柱轴时截线为圆。

一般斜截且不越过端盖时截线为椭圆。

与有限圆柱求交时必须考虑上下端盖和侧面边界。

采样曲线必须按参数连续排序。

采样密度应由视觉误差或可配置教学质量决定。

拖动时可使用较低预览质量。

交互结束后必须恢复最终质量。

解析特殊情形应保留语义，便于显示“圆”或“椭圆”。

## 22. 圆锥截交

圆锥使用有限单叶圆锥模型，除非功能明确要求双叶延拓。

截交必须考虑顶点、底面和有限高度。

截线可能为圆、椭圆、抛物线式开放片段、双曲线式片段或退化线。

有限实体上的结果可能被边界截断。

教学标签不得仅凭外观猜测圆锥曲线类型。

分类应根据平面法向量与圆锥半顶角关系完成。

接近分类边界时使用容差并显示“临界”状态。

曲线采样不得跨越不连续分支强行连线。

## 23. 球截交

球与平面的截线为空、点或圆。

设球心到平面的有符号距离为 `h`。

若 `abs(h) > radius + tolerance`，结果为空。

若 `abs(abs(h) - radius) <= tolerance`，结果为切点。

否则截圆半径为 `sqrt(radius² - h²)`。

截圆圆心为球心沿平面法向量的垂足。

显示采样点应位于截平面基底中。

不得通过三角网格边交点拟合球截圆作为最终结果。

## 24. 截面输出模型

截交算法输出不得直接是渲染对象或屏幕坐标。

输出应包含截面类型、三维点、闭合状态、曲线语义和来源实体 ID。

多边形可包含有序顶点与边来源映射。

曲线可包含参数区间和采样点。

输出应能直接驱动三维高亮与三视图投影。

同一截面数据必须同时作为两个视图系统的来源。

不得在正投影视图中重新计算另一套截交。

## 25. 截面渲染

截面轮廓应明显区别于实体边线。

截面填充应半透明并避免严重 Z-fighting。

优先使用合理的渲染层、polygon offset 或轻微法向偏置。

偏置只属于渲染层，不得写回几何数据。

闭合多边形三角化应在截平面二维坐标中完成。

凹多边形不得使用简单扇形三角化。

曲线轮廓必须处理闭合端点重复问题。

更新动态 BufferGeometry 时应复用缓冲区或正确释放旧资源。

## 26. 相贯线边界

实体相贯属于未来独立模块。

截面算法不得硬编码第二个实体。

相贯线算法必须保留构造过程所需的中间数据。

只显示最终曲线不足以满足教学目标。

未来实现应支持母线法、辅助平面法或辅助球面法等教学步骤。

当前提交不得以粗糙布尔库替代可解释过程并称为完成。

## 27. 变换规则

领域对象应保存局部几何和对象变换。

求交可将截平面变换到实体局部空间，或将实体几何变换到世界空间。

同一算法必须坚持一种空间。

变量名称应标明 `local`、`world`、`view` 或 `screen`。

法向量变换必须使用逆转置矩阵。

存在非均匀缩放时不得用普通方向变换替代。

矩阵求逆失败必须显式处理。

对象变换更新后应调用必要的世界矩阵更新。

不得依赖渲染循环碰巧更新矩阵后才获得正确结果。

## 28. 渲染资源所有权

当前渲染层是 Canvas 2D：绘制对象是每帧重建的路径、屏幕点与样式字符串，没有需要在代码中显式释放的 GPU 资源；本节规定的是画布、上下文与缓存的持有边界。

画布节点与 2D 上下文由页面实例持有，`initializeCanvas()` 是唯一创建入口。

`onUnload()` 必须解绑画布、上下文与缓存（`sectionSolidCache`、`sectionResultCache`），不留悬空引用。

交互状态（`canvasDragging` 等）属于生命周期资源，拖动结束与离开页面时必须复位。

绘制函数不得把上下文、画布或缓存挂到模块级变量；跨调用共享的状态只能来自页面实例。

单次绘制内产生的临时数组、路径与对象应随绘制结束丢弃，不得无界累积。

若将来引入 WebGL 或离屏画布，必须重新定义“谁创建、谁持有、何时释放”的资源所有权，不得沿用本节。

## 29. 几何复用与缓存

几何真值只保存在领域数据中（`this.data` 的点、直线、平面与立体参数）；绘制层不得另存一份真值。

绘制层只读领域数据；高亮、选中、线型等仅作为绘制参数传入，不得写回。

复用计算结果必须经过缓存，缓存键必须包含影响结果的全部参数（截面缓存的 `resultKey`）。

缓存必须有明确失效点：参数变化、模式切换与会话结束都必须失效或清空。

缓存不得跨会话、跨模式残留。

需要独立修改的数据不得与其它对象共享同一可变引用；应先复制再改（如展开 `{ ...point }`）。

基本立体与截交结果分别由 `basic-solid.js`、`section-geometry.js` 计算，绘制层只调用、不重算。

为复用而牺牲可读性或正确性不被接受。

## 30. 重绘调度与性能

只有一个重绘入口 `scheduleCanvasDraw()`；子模块不得各自创建绘制循环。

重复的重绘请求必须合并到同一帧，用调度标志（`_drawScheduled`）去重。

优先使用画布自带 `requestAnimationFrame`，不可用时退化为 16ms 定时。

静态状态按需重绘，不保留常驻动画循环。

拖动过程中只更新内存值并请求重绘，`setData` 只在拖动结束时提交一次。

每帧不得重复执行节点查询或布局量算；`createSelectorQuery` 只用于初始化。

设置画布 `width`/`height` 会重置变换矩阵，之后必须重新应用设备像素比缩放（`context.scale`）。

设备像素比缩放必须设上限（当前为 3），避免低端设备过度绘制。

屏幕坐标一律使用逻辑像素；命中阈值等交互常量不得随像素比变化。

优化前必须先确认热点；不得以牺牲几何正确性换取不可测量的微优化。

## 31. 视图与投影布局

空间视图使用固定斜轴测基底（X 向左下、Y 向右下、Z 向上），**不提供自由旋转**；不得为“可旋转”引入相机系统。

三面投影使用固定正投影：正视 (x, z)、俯视 (x, -y)、侧视 (-y, z)，展开关系必须符合第一角约定（§10）。

布局由 `getLayout()` 唯一决定（上方空间视图约占 46%，下方为三面投影展开区）；绘制函数不得自行推导位置或比例。

比例尺统一由布局单位长度决定；空间视图与三个投影视图必须共用同一套坐标映射（`projectIsometric` 与 `worldToView`）。

空间点与其三个投影点必须来自同一几何真值，并使用同一映射。

重置必须恢复完整布局与默认教学状态（`handleReset()`）。

不得用极端缩放或裁剪掩盖尺度设计问题；教学坐标范围 0..8 的对象必须完整落在可视区域内。

## 32. 拾取与选择

拾取判定在屏幕（逻辑像素）坐标中进行，命中阈值统一（当前 30）。

只有点、直线、平面三种模式提供拖动入口；截面模式与立体模式不得触达拖动路径。

可拾取对象限定为当前模式的控制点：点模式取点，直线模式取两个端点，平面模式取三个顶点。

拾取候选限定在三面投影视图内；空间视图不参与拾取。

命中判定必须使用当前布局量算出的屏幕位置，不得使用过期尺寸或缓存坐标。

命中顺序必须确定（按 a → b → c 依次判定），不得依赖不确定的遍历顺序。

同一时刻只允许一个拖动主体（`draggingProjection` / `draggingLineProjection` / `draggingPlaneProjection` 三选一），开始新拖动前必须清除旧状态。

选中与拖动状态只有一份权威存储（页面 data 或实例属性），绘制层只读。

拖动结束、切换模式或重置后必须清除选中与拖动引用。

## 33. 拖动交互

拖动只发生在三面投影视图内；空间视图不参与拖动（与“直接拖三维对象”是两种交互）。

拖动开始时必须记录被拖对象、被拖的键与视图类型（如 `draggingPlaneProjection = { pointKey, viewType }`）。

拖动只修改该视图可见的两个坐标，第三个坐标保持原值：正视改 x/z，俯视改 x/y，侧视改 y/z。

屏幕位移必须换算为模型值（`screenToModel`），不得把像素增量直接累加进世界坐标。

换算结果必须取整并钳制在教学模型范围（0..8）内——模型坐标是整数语义。

拖动期间必须锁定页面滚动（`canvasDragging` 驱动滚动容器），否则手势会被滚动容器吞掉。

语义校验必须在写回前完成：平面三点共线时放弃本次更新（`isPlaneNonCollinear`）。

拖动使对象不再符合当前预设类型时，类型必须回退为一般情形（`general`），且不得与预设冲突。

拖动结束必须清理全部拖动状态并恢复滚动。

拖动应形成一次语义操作；若将来实现历史系统，应可直接接入撤销。

## 34. UI 状态机

工具模式应通过显式状态机管理。

推荐状态包括选择、建点、建线、建面、建实体、截切和动画。

模式切换必须取消未完成的临时操作。

取消操作必须清理预览对象和监听状态。

工具按钮的视觉状态应来自同一模式状态。

不得让多个互斥工具同时激活。

键盘 Escape 应优先取消当前临时操作。

## 35. 状态栏

状态栏显示当前坐标、选中对象、投影信息和相机状态。

坐标精度应统一配置。

未命中场景时不得显示陈旧坐标而不加说明。

对象信息应使用教学名称而不是内部类名。

异常和退化几何应提供简短可理解提示。

状态更新不得成为高频 DOM 性能瓶颈。

## 36. 动画系统

动画应解释过程，而不只是让对象移动。

每个教学动画由可命名步骤组成。

步骤应声明起始状态、目标状态、持续时间和解释文本。

暂停后恢复必须连续。

改变速度不得改变最终几何状态。

拖动时间轴必须可确定地重建状态。

不得依赖从上一帧增量累加来实现可跳转时间轴。

推荐由标准化时间 `t` 计算状态。

分步模式必须停在有教学意义的关键帧。

动画结束后领域模型与画面必须一致。

## 37. 教学呈现

新功能必须回答“学生能从画面中发现什么”。

重要对应关系应通过颜色、连线或同步高亮呈现。

颜色不能是唯一编码方式。

应配合线型、标记、标签或位置编码。

动画中一次只强调必要信息。

辅助构造应可隐藏但默认在教学步骤中可见。

数值结果应伴随几何含义。

不可用纯公式面板取代动态空间展示。

## 38. 可访问性

所有工具按钮必须有文本或可访问名称。

键盘焦点必须可见。

颜色对比度应适合教室投影。

红绿轴除颜色外还必须有 X、Y 标签。

状态变化不应只靠短暂颜色闪烁表达。

滑块应显示当前值和单位。

触控目标应有合理尺寸。

响应式布局不得让核心控制不可达。

## 39. 响应式布局

小程序端为上下布局：上方是空间视图，下方是三面投影展开区（当前约占 46% / 54%）。

网页版（`web/`、`web-release/`）可采用左右排列，窄屏时改为上下排列。

布局变化后必须按新尺寸重设画布 backing size 与设备像素比缩放，并重算布局单位长度。

二维投影视图也必须重算视口。

不得仅设置 CSS 尺寸而忽略 canvas backing size。

应考虑 `devicePixelRatio` 并设置合理上限。

## 40. 命名规范

类、构造器和工厂类型使用 `PascalCase`。

函数、变量和实例使用 `camelCase`。

常量使用 `UPPER_SNAKE_CASE`。

文件名使用现有项目风格；初始建议小写单数名。

布尔值使用 `is`、`has`、`can`、`should` 或明确动词前缀。

事件处理函数使用 `handleXxx`。

注册监听函数使用 `onXxx` 或 `addXxxListener`。

转换函数必须包含来源和目标。

不得使用 `data`、`temp`、`obj` 等含义不清的长期变量名。

短循环变量和明确数学推导中的 `p`、`n`、`t` 可接受。

领域名称优先采用准确英文，中文用于 UI 和解释注释。

## 41. 函数设计

函数应只有一个清晰职责。

函数名称应描述结果或动作。

避免布尔参数控制完全不同的行为。

超过三个相关参数时优先使用命名选项对象。

公共函数必须验证关键前置条件。

内部高频函数可在调用链已验证时省略重复检查。

副作用必须从名称或文档可见。

禁止隐式读取可变全局状态。

## 42. 类与组合

优先组合而非深继承。

领域模型不得依赖渲染层对象。

可将 `renderObject` 作为适配器持有，但要明确所有权。

通用行为通过小型服务或策略组合。

禁止建立 Point、Line、Plane、Solid 的庞大万能基类。

只有真正稳定且共享的契约才抽象接口。

## 43. 事件与数据流

领域变更应发出语义事件。

例如 `point:moved`、`plane:changed` 和 `section:updated`。

事件负载必须包含对象 ID 和必要的新状态。

不得把整个场景对象作为默认事件负载。

事件订阅必须可解除。

销毁模块时必须解除全部订阅。

避免事件 A 触发 B、B 又隐式触发 A 的循环。

批量更新应支持暂停通知或合并通知。

## 44. 错误处理

用户输入错误应在界面就近提示。

几何退化是正常领域状态，不应全部抛异常。

程序不变量被破坏时应快速失败并提供上下文。

不得用空 `catch` 吞掉错误。

控制台错误应包含模块和对象 ID。

生产交互不得因单个无效对象停止整个渲染循环。

恢复策略必须避免继续传播 NaN。

任何写入场景的位置、矩阵和顶点数据前都应保证数值有限。

## 45. 注释规范

注释解释原因、坐标约定和非显然算法。

不得逐行复述代码。

几何公式注释必须定义符号。

涉及论文、标准或算法来源时应注明名称和链接信息。

临时 TODO 必须写明缺失行为和触发条件。

禁止留下无负责人语义的“以后优化”。

复杂截交函数应说明输入空间、容差和退化返回值。

## 46. CSS 规范

主题颜色和尺寸使用 CSS 自定义属性。

轴色、投影面色和教学高亮色应集中定义。

组件状态使用类或数据属性，不使用大量内联样式。

禁止依赖脆弱的深层 DOM 选择器。

画布容器必须正确处理 `min-width: 0` 和 `min-height: 0`。

工具栏溢出必须可滚动或折叠。

打印样式只有明确需求时才实现。

## 47. HTML 规范

使用语义化结构。

按钮必须使用 `<button>`，不得用无键盘行为的 `<div>` 模拟。

表单控件必须有 `<label>`。

三维画布和三视图区域应有可访问说明。

脚本加载顺序必须显式且稳定。

如果使用原生 ES modules，必须验证直接打开文件时的浏览器限制。

由于项目要求直接打开 `index.html`，不得未经验证依赖 `file://` 下受限模块行为。

## 48. 性能预算

普通交互目标帧率为 60 FPS。

高频指针事件应合并到渲染帧处理。

截交计算应与实际脏状态绑定。

不得每帧重建所有实体投影。

不得每帧重新创建所有标签 DOM。

大批量点线可考虑 InstancedMesh 或合并缓冲区。

优化必须保留对象级拾取或提供映射。

长期运行后对象数、材质数和纹理数不应持续增长。

可使用 `renderer.info` 辅助检查泄漏。

## 49. 验证层次

纯数学函数应进行确定性测试。

模块集成应验证数据变更触发投影和截面更新。

渲染验证应检查场景对象数量、可见性和资源释放。

交互验证应覆盖选择、拖动、模式切换和取消。

手工验证应覆盖直接打开 `index.html`。

至少在目标浏览器中检查控制台无未处理错误。

不得仅凭“页面能打开”宣称几何功能正确。

## 50. 点与线测试基准

测试原点和三个轴上的点。

测试正负坐标。

测试两个端点交换后真长不变。

测试水平线、正平线、侧平线及投射线分类。

测试零长度线被拒绝。

测试线接近分类边界时结果稳定。

测试移动端点后三个投影视图同步。

## 51. 平面测试基准

测试三非共线点定平面。

测试三共线点被识别。

测试 H、V、W 平面。

测试一般位置平面。

测试平面与投影面平行、相交和重合。

测试旋转后法向量保持单位长度。

测试平移后法向量不变。

## 52. 多面体截面测试基准

测试截平面完全位于实体外。

测试穿过实体中心。

测试穿过单顶点。

测试包含一条边。

测试与一个面共面。

测试非常接近面但不共面。

测试旋转、平移和缩放后的实体。

测试截点无重复。

测试多边形顶点顺序连续且法向一致。

测试三维轮廓与三视图来自相同数据。

## 53. 曲面截面测试基准

圆柱测试横截圆、斜截椭圆、轴向截面和端盖边界。

圆锥测试横截圆、一般椭圆、临界平行母线和过顶点退化。

球测试不相交、相切、过球心和一般截圆。

测试极小与极大尺度。

测试交互预览和最终质量结果拓扑一致。

测试闭合曲线无可见断口。

## 54. 回归检查

新功能不得破坏点、线、平面基础交互。

新功能不得改变第一角投影布局。

新功能不得让隐藏的辅助对象参与选择。

新功能不得造成相机控制冲突。

新功能不得导致删除对象后 GPU 资源持续增长。

新功能不得改变无关对象的标签或 ID。

涉及公共数学函数时必须检查全部调用方。

## 55. 测试数据原则

使用容易人工判断的几何构型作为基准。

优先使用原点、单位轴、对称实体和整数坐标。

同时加入非对称和非整数案例防止偶然通过。

随机测试必须固定种子并记录失败输入。

视觉快照不能替代数值不变量测试。

数值测试应比较容差而非格式化字符串。

## 56. 兼容性

保持现代桌面浏览器兼容。

不得依赖未经降级说明的实验 API。

使用 Pointer Events 统一鼠标和触控时应处理 pointer capture。

画布节点或 Canvas 2D 能力不可用时应显示清晰提示，不得静默停在空白画布。

页面从 `file://` 打开时核心路径必须工作。

本地资源路径必须使用相对路径并注意大小写一致性。

## 57. 安全与稳健性

用户输入不得通过 `innerHTML` 直接插入。

标签文本使用 `textContent`。

导入数据若未来实现，必须验证类型、范围和有限数值。

不得执行导入数据中的脚本或表达式。

外部资源失败不得让已加载教学功能整体崩溃。

## 58. 版本与迁移

领域数据格式应包含版本号。

格式变更必须提供迁移策略或明确不兼容原因。

不得无声改变坐标轴语义。

不得无声改变投影展开方向。

不得复用旧字段表达新的不同含义。

已公开 ID 必须保持稳定。

## 59. 变更范围控制

修复局部缺陷时优先局部修改。

需要架构调整时先描述问题、风险和渐进方案。

不得因个人偏好重命名全部模块。

不得在功能提交中混入全仓格式化。

不得重写已工作的算法，除非有可复现错误、明确需求或可验证收益。

替换算法时必须保留或扩充回归案例。

## 60. 提交质量门槛

代码必须可读且职责清晰。

不得留下调试日志、断点或临时可视对象。

不得提交未使用的大型依赖或资源。

不得提交生成缓存。

所有新增资源必须有使用位置和所有权。

所有新增控件必须连接实际行为或明确禁用。

所有新增对象必须有删除或销毁路径。

## 61. 完成定义

功能行为符合当前任务。

几何结果在正常与退化案例中合理。

三维场景和三视图同步。

交互期间无明显卡顿。

对象删除与模块销毁无明显泄漏。

直接打开 `index.html` 可运行。

现有功能完成必要回归检查。

文档与实际行为一致。

交付摘要完整。

## 64. 最终原则

空间关系必须比数值面板更直观。

几何真值必须独立于渲染对象。

投影与截面必须共享同一领域数据来源。

退化情形必须被建模，而不是被忽略。

交互必须即时反馈，同时保持最终结果准确。

渲染资源（当前为 Canvas 2D）必须有明确所有者和释放路径。

算法必须可解释、可测试、可扩展。

每次改动必须保护已工作的教学能力。

当简洁与炫技冲突时，选择简洁。

当速度与不可见的错误冲突时，选择正确并进行有依据的优化。

当最终图形与学习过程冲突时，同时呈现构造过程。

本平台的成功标准不是能画多少对象，而是学生是否更容易看懂空间与投影的对应关系。
