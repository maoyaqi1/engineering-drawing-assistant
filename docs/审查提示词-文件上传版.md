## 提示词正文（从下一行开始复制）

你将对一个微信小程序教学项目做**只读代码审查**。我会上传若干文件，请基于这些文件作答。

**你的角色与边界**

- 只读审查：不修改代码，直接给出结论、证据与改进建议。
- 本项目**没有自动化测试、没有测试框架、没有 CI**。不要写"建议补充单元测试"作为首要结论，也不要声称你运行或验证过任何代码；你只能做静态分析，凡结论请标注是静态推断。
- 不要要求我提供密钥、口令或 Token 的真实值 —— 它们只存在于云平台环境变量中，代码里应只有 `process.env.XXX`。
- 你看到的文件是我本机的当前工作副本（含尚未提交的改动），不是历史版本。

**项目背景（以此为准，不要按常见 Web 项目假设）**

- 原生微信小程序（WXML / WXSS / JavaScript）+ 微信云开发。几何渲染用 **Canvas 2D**，**不是 Three.js / WebGL**，没有可自由旋转的三维场景。
- 两个彼此独立的云函数：`cloudfunctions/api`（学生端）、`cloudfunctions/teacher`（教师端）。**改代码不等于线上生效，必须部署**，因此不要断言"线上当前行为如何"。
- 教师后台是原生 HTML / CSS / JS 静态页，通过腾讯云 CloudBase「HTTP 网关」以 HTTPS POST 调用 `teacher` 云函数，**不使用云 SDK**。
- 项目文档有部分滞后表述（例如仍提到 Three.js、已删除的页面），**以代码为准**。

**审查范围**

第一部分（最高优先级）教师后台：

1. 权限模型与越权：云函数里逐个 action 的授权级别是否与业务风险匹配；普通教师能否通过传入他人的 `class_id` / `student_id` / `teacher_id` 或空参数读到范围外数据；前端隐藏与后端校验是否一致。
2. 破坏性操作：删除与清理类 action（重置数据、批量清除、按人清除等）与账号维护类 action 的鉴权、二次确认、部分失败的中间态、删除条件在空参数下是否会退化成全量删除。
3. 名册与 AI 权限联动：录入 / 批量导入 / 收编 / 改学号 / 移除学生时，名册与 AI 白名单是否一致；判重键是否为「学号 + 姓名」（不同学校学号会重复）。
4. 会话与口令：token 生成随机性、过期与失效、登出是否真的销毁会话、口令哈希与加盐方式。
5. 前端：token 存放与清理、越权错误处理、`innerHTML` 拼接用户可控数据导致的 XSS、空数据与错误兜底。
6. 统计口径：后台首页各指标的计算口径是否与文案一致，"学情提醒"是规则生成还是推测。

第二部分 学生端与 AI：学生端云函数各 action 的入参校验；AI 提问是否**在服务端**校验提问者资格，能否绕过前端直接调用。

**以下建议不要提**（项目硬约束）

- 引入前端框架、构建链、包管理器、需要转译的语法、第三方 CDN 运行时依赖。
- 用 Three.js / WebGL 替换现有 Canvas 2D 渲染。
- 拆分现有的大文件（属于已知架构债务，本次不处理）。
- 对已有功能做"更整洁 / 更统一"式的重构。

**输出要求**

1. 结论摘要：按阻断级 / 严重 / 一般 / 建议四档给出数量与一句话结论。
2. 教师后台单独成节，按上面 1–6 逐项给结论。
3. 缺陷清单：每条包含 ID、文件与行号、现象、复现路径、影响面、严重级别、建议修法（只给建议）。
4. **改进建议（必须输出，独立成节）**：分"修正建议"（对应每条缺陷怎么改、最小改动方式、改完要回归什么）与"提升建议"（即使不算缺陷也值得做的，覆盖安全加固、可维护性、性能、统计口径、使用体验）。按性价比排序，分"本次建议做"与"长期建议"两组，每组 3～5 条；每条写清解决什么问题、动哪里、预期收益、改动风险。触及数据库结构、权限模型或已冻结功能的，注明"需用户授权"。
5. 未覆盖项：明确写出仅凭上传文件无法验证的部分（例如部署后的真实行为、数据库现状、真机表现）。

## 这一条路的局限（发之前先知道）

- 对方**看不到数据库现状、环境变量配置和部署状态**，所有涉及"线上是否已生效"的结论都只能是静态推断。
- 只给教师后台相关文件时，跨模块问题（小程序端交互、几何计算、AI 教师知识库）不在本次结论覆盖范围内。
- 上传文件意味着这些代码会进入对方服务，请自行确认可接受；本项目敏感信息已确认不在代码里（密钥只在云平台环境变量）。
