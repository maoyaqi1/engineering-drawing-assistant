# 用户与鉴权模型（学生端 · 2026-09-14 更新 · 第二阶段）

> 适用范围：小程序学生端（`pages/`、`utils/api.js`）与学生端云函数 `cloudfunctions/api`。
> 教师端只负责录入名册，不适用本文的放行判定。
> 变更摘要（第二阶段）：判定源从 `roster` 白名单改为 `students` 名册 + `classes` 班级状态；
> 新增 `class_archived` / `no_class` 两个原因与 fail closed；`roster` 集合与写入通道已下线。

## 角色

1. **在册学生**：微信登录 + 填写学校/姓名/学号，且「学号 + 姓名」命中教师名册，**且该行所在班级为 `active`**。
2. **游客**：已登录但未填资料（未注册游客），或资料与名册不一致（已注册游客），或命中名册但班级已停用 / 未分班。
3. **教师**（含超级管理员）：名册与班级的唯一录入端，见 `cloudfunctions/teacher`。

## 规则

1. **教师是名册唯一录入端**：只有教师端能创建/导入/修改/删除名册（`students`）。学生端不得写名册、不得「申请入册」、不得自动入册；`register` 只写 `users`。白名单集合 `roster` 已下线（仅保留 `roster.status` 这个 action 名）。
2. **匹配键恒为「学号 + 姓名」**：两端使用同一套规范化（学号 = trim + 去内部空白 + 全角转半角、大小写敏感；姓名 = trim + 压缩连续空白）；必须两项同时一致才放行，禁止只用学号（不同学校学号规则可能重复）。
3. **学校不参与放行**：学校字段仅用于展示与统计。
4. **游客保留基本功能**：点 / 线 / 面、基本立体、平面切割立体等全部互动教学功能与学习埋点（`session.start`、`session.end`、`record.event`、`statistics`）对游客正常开放。
5. **AI 教师提问属名册权益**：`ai.ask` 以及 `ai.list` / `ai.detail` / `ai.feedback` 必须在服务端校验，禁止只靠前端隐藏按钮。
6. **游客被拒时区分原因**（四类）：`no_profile`（未填姓名学号）、`not_in_roster`（已填但不在名册）、`class_archived`（班级已停用）、`no_class`（命中名册但未分班）；另有 `check_failed`（读 `classes` 失败，fail closed，可重试）。
7. **服务端是权威**：名册被删除或改名后，学生端再次提问会被服务端重新校验并立即收回权限，不依赖前端缓存。
8. **登录门槛**：`pages/index`、`pages/ai`、`pages/survey` 必须先登录；`pages/terms` 允许匿名查看。未注册游客仍可进入首页并使用互动工具（只是不能用 AI 与问卷）。
9. **问卷同口径**：问卷的邀请与提交都只面向「命中名册的在册学生」。
10. **测试账号 = 全功能开放**（2026-09-14 决策，覆盖原 A1-补）：测试账号包括两类——
    `INTERNAL_OPENIDS`（云函数环境变量）里的内部账号（登录时强制覆盖写 `is_internal`，人工不可改），
    以及在教师后台被人工标为 `test` 的账号（`users.data_quality = 'test'`）。
    只要属于测试账号，**所有功能都可用**（AI 教师、问卷、互动），**不设名册 / 班级门槛**，即使还没填姓名学号也可用；
    它们的使用**不计入真实学情**——隔离由报表分线完成（`internal` / `is_demo` / `test` 三条线从学情与游客漏斗里排除）。
11. **只有超级管理员可以标 `test`**：`data.markQuality`（及 `data.backfillQuality`）仅超管可调，普通教师 403；
    学生端无法自封——`register` / `login` 忽略客户端传来的 `data_quality` / `is_internal`，
    新账号一律按 T0 规则写 `production` / `unknown`，`is_internal` 只由环境变量 `INTERNAL_OPENIDS` 决定。
12. **普通游客不受影响**：未标 `test`、也不在 `INTERNAL_OPENIDS` 里的账号，仍严格按 1–7 条判定（登记在册才能用 AI）。

## 单一入口

学生端云函数 `cloudfunctions/api` 的 `resolveAccess(user)` 是唯一鉴权入口，返回
`{ level: 'student' | 'guest', reason: 'ok' | 'no_profile' | 'not_in_roster' | 'class_archived' | 'no_class' | 'check_failed', in_roster, is_internal, class_name }`；
`roster.status` 直接返回该结果（并回显 `name` / `student_id` / `profile_completed`），AI 相关 action 统一据此拒绝
（`NO_PROFILE` / `NOT_IN_ROSTER` / `CLASS_ARCHIVED` / `NO_CLASS` / `ACCESS_CHECK_FAILED`）。

判定顺序（判定不缓存，每次实时重算）：

```text
测试账号（is_internal 或 data_quality=test）→ 直接放行（全功能；不计入学情）
未填齐姓名 + 学号 → no_profile
按规范化学号按键查询 students（上限 2000 条）→ 未命中 → not_in_roster
命中：班级为空 → no_class
     读 classes 失败 → check_failed（fail closed）
     班级 status ≠ active → class_archived
     否则 → ok
```

返回值还包含 `test_account`（是否测试账号）与 `bypass`（`internal` / `test`），供前端提示"本次使用不计入真实学情"。

会话与事件写入 access 快照（`access_level` / `access_reason` / `in_roster` / `is_internal` / `access_test_account`），
**写入后永不更新**；其中 `access_test_account` 记录"当时是否测试账号"，用于确保测试过程不被当成学习数据。

离线用例：`scripts/offline/run-access.cjs`（基础模型）与 `scripts/offline/run-access2.cjs`（第二阶段的四态、fail closed、快照、问卷、权限收窄），`node scripts/run-all.js` 会自动运行。
